# NUMA_Locality_Aware_Scheduling_48core-Simulation-in_Gem5

Locality-aware task scheduling and data distribution on a **simulated 48-core,
8-node NUMA machine in gem5**, reproducing:

> A. Muddukrishna, P. A. Jonsson, M. Brorsson,
> **"Locality-Aware Task Scheduling and Data Distribution for OpenMP Programs
> on NUMA Systems and Manycore Processors"**, Scientific Programming, 2015.

The paper ran on a real 4-socket AMD Opteron 6172 (8 NUMA nodes × 6 cores,
distances 10 / 16 / 22). We don't have that machine, so we built it in gem5,
patched gem5 so pages really live on NUMA nodes, wrote a task runtime with the
paper's two scheduling algorithms, and ran the paper's Figure 7 experiment.
The TILEPro64 part (Algorithm 3) is skipped because that chip no longer exists.

**Headline:** 112 gem5 runs plus a GPU experiment, all verified correct. The
simulated machine matches the paper's latency ratios (1.00 : 1.61 : 2.22).
Locality-aware + coarse distribution makes Map **0.82×** the baseline time,
and **0.70×** when the inter-node links are twice as slow.

## 2. Results

### Machine check (paper Figure 2)

Memory latency from node 0 (`bench/latency.c`):

| target node | NUMA distance | cycles per load | ratio |
|---|---|---|---|
| node 0 (local) | 10 | 151 | 1.00 |
| nodes 1, 2, 4, 6 (1 hop) | 16 | 243 | 1.61 |
| nodes 3, 5, 7 (2 hops) | 22 | 335 | 2.22 |

### Main experiment (paper Figure 7), `results/summary.csv`

Simulated time of the parallel region, normalized to work-stealing + numactl
interleave (= 1.00). Lower is better. `ws` = work-stealing, `la` =
locality-aware; `standard` = Linux first-touch.

| benchmark | ws-fine | ws-coarse | la-fine | la-coarse | ws-standard | la-standard |
|---|---|---|---|---|---|---|
| Map | 1.05 | 1.12 | 1.06 | **0.82** | 2.42 | 2.67 |
| Vecmul | 0.99 | 1.18 | 1.40 | 1.01 | 1.82 | 1.73 |
| Matmul | 1.00 | 1.00 | 1.49 | 0.99 | 1.00 | 1.48 |
| Jacobi | 1.00 | 1.01 | 1.44 | 1.39 | 1.02 | 1.38 |
| Reduction | 1.01 | 1.07 | 1.10 | 0.99 | 0.97 | 0.93 |
| SparseLU | 0.98 | 1.00 | 1.22 | 1.24 | 1.00 | 1.24 |

**Matches the paper:** Map wins clearly with la-coarse (each task runs on the
node holding its vector; miss latency 160 vs 314 cycles). Fine distribution is
a good replacement for numactl (ws-fine within 5% everywhere). Map and Matmul
lose with la-fine, for the paper's own reason: an even spread sends every task
to one local queue.

**Differs from the paper:** la is slower on Jacobi and SparseLU. The cause is
our small inputs (64 tasks for 48 cores instead of ~1024): Algorithm 1 puts
every task in one node's queue, and Algorithm 2 lets another node steal only
while that queue holds more than `distance × 6` tasks, so many cores sit idle.

| test | result |
|---|---|
| remove the steal limit (`RT_STEAL_DIST=none`), `results_steal_none/` | every slow case back to 1.00–1.03× |
| Jacobi 256 tiles, `results_jacobi_256tiles/` | la-fine 1.44× → 1.15× |
| Jacobi 1024 tiles = paper scale, `results_jacobi_paperscale/` | la-fine 1.03×, la-coarse 1.07× |

### Extended experiments (`extended_experiments.sh`)

**Scaling: same 48 cores as 8 × 6, 4 × 12 or 2 × 24 nodes** (`results_scaling_n4/`, `results_scaling_n2/`)

| run | 8 nodes | 4 nodes | 2 nodes |
|---|---|---|---|
| Map la-coarse | 0.82 | 0.83 | 0.89 |
| Map la-fine | 1.06 | 1.63 | 0.95 |
| Jacobi la-fine | 1.44 | 1.47 | 1.00 |
| Matmul la-fine | 1.49 | 1.50 | 1.00 |

The locality win grows with node count. At 2 nodes the steal-rule slowdowns
vanish (24 local cores share the busy queue).

**Steal distance: OS value (16 / 22) vs hops (1 / 2)** (`results_steal_os/`)

| run | hops | OS distance |
|---|---|---|
| Jacobi la-fine | 1.44 | 5.25 |
| Matmul la-fine | 1.49 | 5.47 |
| SparseLU la-coarse | 1.24 | 2.34 |

With the OS value not a single task is stolen; all work stays on one 6-core node.

**Slower links: hop latency 45 → 90 cycles** (`results_hoplat90/`), la-coarse

| | Map | Vecmul | Matmul | Jacobi | Reduction | SparseLU |
|---|---|---|---|---|---|---|
| normal links | 0.82 | 1.01 | 0.99 | 1.39 | 0.99 | 1.24 |
| slow links | **0.70** | **0.85** | 0.99 | 1.32 | **0.90** | 1.10 |

The bigger the NUMA penalty, the more locality-aware scheduling pays off.

**Real hardware** (`results/hardware_baseline.txt`): the 24-core workstation
that ran everything has 1 NUMA node (distance 10 only), which is why the
experiment needs a simulator.

### GPU locality experiment (`gpu/`)

A CPU + discrete GPU is a 2-node NUMA machine with PCIe as the link. Map
pattern, 256 MB, NVIDIA RTX 4000 Ada (`gpu/results/gpu_locality.txt`):

| placement | like | kernel | total |
|---|---|---|---|
| explicit copy first | coarse | 1.8 ms | 137.8 ms |
| managed, CPU first-touch | first-touch | 36.0 ms | 124.0 ms |
| managed + prefetch | locality-aware | 1.7 ms | **108.8 ms** |

Migrating pages on fault makes the kernel ~22× slower; prefetching ahead of
time is fastest overall. 8 CUDA streams beat 1 stream by only ~9% because the
PCIe copy dominates.

### Improvements beyond the paper (`improvements_experiments.sh`)

Two additions to the locality-aware scheduler. Both are new options, so the
paper's behaviour is unchanged when they are off.

**Improvement 1: NUMA cost-aware work stealing** (`RT_STEAL_DIST=cost`).
The paper lets a node steal only if another queue holds more than
distance x cores-per-node tasks, and it stops at the first such queue. With few
tasks this leaves cores idle. The cost rule steals from node *i* when

    backlog of node i  =  queued tasks x average task time / cores per node
      >  extra memory time of the task on our node
       =  sum over nodes j of  cache lines of its data on j x 92 x (our hops to j - i's hops to j)

The average task time is measured by the runtime as it runs (until the first
task finishes it falls back to the hop rule). A rejected task goes back to the
tail of its queue and the search goes on to the next-nearest node. The 151 / 92
cycle latency model comes from our latency probe (`RT_LAT_LOCAL`, `RT_LAT_HOP`).

**Improvement 2: adaptive data distribution** (`OMP_DATA_DISTRIBUTION=adaptive`).
Start from the baseline (fine). Switch an allocation to coarse only with evidence:
- *size rule*: smaller than one page per node, so fine cannot spread it evenly;
- *profile rule*: a profile run (`RT_PROFILE_OUT`) showed each task that uses
  the allocation lists at least half of it (a task works on the whole block).

Everything else stays fine. The profile records, per main-program allocation,
how many tasks list it and how many bytes they list (`profiles/<bench>.prof`),
and the real run reads it back with `RT_PROFILE_IN`. Pages are never moved:
the choice is made when the allocation is created, so the gem5 NUMA patch is
unchanged.

Run everything with `bash improvements_experiments.sh`. Results go to
`results_improvements/` (`IMPROVEMENTS_RESULTS.md`, `improvements.png`,
`summary.csv`), with new configs `la-fine-cost`, `la-coarse-cost`,
`la-adaptive` and `la-adaptive-cost`.

## 3. How the paper maps to the code

| Paper | Our code |
|---|---|
| 8-node, 48-core Opteron machine (Fig. 1) | `gem5-config/numa_machine.py` |
| NUMA distances 10 / 16 / 22 | 8 routers; 1 hop = 16, 2 hops = 22 |
| First-touch page placement (OS default) | gem5 patch: page goes to node of the core that touches it first |
| `numactl` / libnuma page placement | gem5 patch: `mbind`, `set_mempolicy`, `get_mempolicy` work in SE mode |
| `omp_malloc` (Listing 2) | `rt_malloc()` |
| `omp_malloc_specific` | `rt_malloc_specific(size, RT_DIST_FINE / RT_DIST_COARSE)` |
| `OMP_DATA_DISTRIBUTION=standard\|fine\|coarse` | same env variable |
| Table 1: fine = pages round-robin | `mbind(MPOL_INTERLEAVE, all nodes)` |
| Table 1: coarse = per-allocation round-robin | `mbind(MPOL_BIND, next node)` |
| Work-stealing baseline (one deque per core) | `RT_SCHED=ws` |
| Locality-aware scheduler (one queue per node) | `RT_SCHED=locality` |
| Algorithm 1 (work-dealing) | `deal_work()` in `numa_rt.c` |
| Algorithm 2 (work-finding) | `find_work_locality()` in `numa_rt.c` |
| Task data footprint from `depend` clause | `rt_dep_t` list given to `rt_task()` |
| Thread timelines (Fig. 8) | `RT_TRACE=file.csv` + `plot_results.py --timeline` |
| Dispatch stall cycles | Ruby memory latency stats in gem5 `stats.txt` |

### Algorithm 1 (work-dealing), in our code

```
D[node] = bytes of the task's depend list on each node   (from rt_malloc records)
if sum(D) > LLC_of_node / cores_per_node  and  D is not perfectly even:
    put the task in the node queue with the lowest  sum_j D[j] * distance(l, j)
else:
    put it in my own node's queue
```

### Algorithm 2 (work-finding), in our code

```
if my node queue has work: take from it
else: for other nodes, nearest first:
          if size(Q_i) > distance(i, me) * cores_per_node: steal one, stop
      nothing found -> exponential back-off, then sleep until new work
```

`distance` in Algorithm 2 is the **hop count** by default (1 or 2). The raw OS
value (16 / 22) would need more than 96 queued tasks before any steal, which
stops stealing completely. Set `RT_STEAL_DIST=os` to try the raw values, or
`RT_STEAL_DIST=none` to steal whenever a queue is non-empty.

## 6. Running the experiments

```bash
G=~/gem5/build/X86_MOESI_hammer/gem5.opt

# one benchmark, the paper's 5 configurations, 2 gem5 runs at a time
python3 scripts/run_experiments.py --gem5 $G --bench map --jobs 2

# everything
python3 scripts/run_experiments.py --gem5 $G --bench all --jobs 2

# figures
python3 scripts/plot_results.py                  # results/fig7_style.png
python3 scripts/plot_results.py --timeline map   # results/timeline_map.png
```

Configurations (paper Figure 7):

| name | scheduler | distribution |
|---|---|---|
| ws-numactl | work-stealing | every page interleaved, like `numactl --interleave=all` (the paper's baseline) |
| ws-fine | work-stealing | fine |
| ws-coarse | work-stealing | coarse |
| la-fine | locality-aware | fine |
| la-coarse | locality-aware | coarse |

gem5 is deterministic, so **one run per configuration** is enough (the paper
needed 20 runs because real hardware is noisy).

**How long it takes** on a 24-core workstation (Intel Core Ultra 9 285, 128 GB):
the whole 42-run matrix finishes in about 30 minutes with `--jobs 24`, because every
gem5 run is single-threaded and many run side by side. The slowest single
runs are Matmul (~15 min) and paper-scale Jacobi (~75 min). Use about 3 GB of
RAM per parallel run.

Everything in one go (build, quick test, full matrix, figures):

```bash
bash run_all.sh                 # main experiment, ~1 hour incl. gem5 build
bash extended_experiments.sh    # 4 follow-up studies, ~2 hours
```

## 8. Scaled-down inputs (and why)

The machine shape is the paper's (8 nodes × 6 cores, distances 10/16/22).
Caches and inputs are scaled down together so that simulation finishes in
hours, while **data still does not fit in cache** (otherwise NUMA would not
matter at all).

| | paper | ours |
|---|---|---|
| L1D per core | 64 KiB | 16 KiB |
| L2 per core | 512 KiB (+ 5 MiB L3 per node) | 64 KiB (last level) |
| LLC per node | 5 MiB | 384 KiB |
| Map | 48 × 1 MiB | 48 × 128 KiB |
| Vecmul | 128 × 28 KiB (TILEPro) | 48 tasks × 3 × 64 KiB |
| Matmul | 4096², block 128 | 384², block 48 |
| Jacobi | 16384², block 512 | 1024², block 128, 2 sweeps |
| SparseLU | 8192², block 256 | 16 × 16 blocks of 32² |
| Reduction | 256 MiB, depth 10 | 8 MiB, depth 6 |

Algorithm 1's threshold `LLC / cores` is 64 KiB here. Most benchmarks' tasks
are above it, so the locality-aware path is really used. SparseLU's tasks
(8 to 12 KiB) are below it, so they always stay in the creating node's queue;
this is one reason SparseLU differs from the paper.

## 9. Differences from the paper

* **Simulation, not real hardware.** Timing comes from gem5's models
  (TimingSimpleCPU, Ruby MOESI_hammer, DDR3 controllers), not an Opteron.
* **No L3.** MOESI_hammer has private L1+L2 per core; L2 is the last level.
* **Same queue code for both schedulers.** Both use a lock-protected deque,
  instead of the Chase-Lev lock-free deque in the paper's baseline, so the
  comparison is only about *where* tasks go.
* **Task ordering by `taskwait`**, as in BOTS, not full `depend` dependences.
  The `depend` list is used for the footprint, exactly as in the paper.
* **First-touch ("standard") data is unknown to the runtime**, as in the paper:
  the locality-aware scheduler can only use pages it placed itself.
* **TILEPro64 part (Algorithm 3) is not done**: that chip no longer exists.
* **SparseLU input fix.** With block size 32, the matrix generator gives an
  exactly zero pivot, and LU without pivoting divides 0 by 0 (NaN). We add
  `2 * NB * BS` to the diagonal (diagonal dominance). Every task does the same
  work, and all 7 configurations match the serial checksum (49178.4059).
* **Steal distance in hops** (1 or 2) instead of the OS value (16 / 22); see
  the steal-distance experiment in section 2 for why.

## 10. Useful knobs

| variable / option | meaning |
|---|---|
| `RT_SCHED=ws\|locality` | scheduler |
| `OMP_DATA_DISTRIBUTION=standard\|fine\|coarse` | global distribution |
| `RT_STEAL_DIST=hops\|os\|none` | distance used by Algorithm 2 |
| `RT_TRACE=trace.csv` | write one line per task (for timelines) |
| `NUMA_INTERLEAVE_ALL=1` | interleave every page of the process (`numactl --interleave=all`) |
| `--hop-latency N` (numa_machine.py) | Ruby cycles per router hop |
| `--nodes`, `--cores-per-node` | machine shape (default 8 × 6) |
| `--cpu-type X86O3CPU` | detailed out-of-order cores (much slower) |
| `--first-touch-off` | turn NUMA placement off (everything on node 0) |

The benchmarks also run on a normal Linux PC (no gem5) for quick correctness
checks, e.g. `NUMA_NODES=8 NUMA_CORES_PER_NODE=6 RT_SCHED=locality OMP_DATA_DISTRIBUTION=coarse ./bin/map`.
